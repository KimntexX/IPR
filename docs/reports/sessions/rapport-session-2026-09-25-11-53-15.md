# Compte rendu de session — 25 septembre 2026, 11:53

## Contexte

La session a porté sur le traitement des images dans IPR, en particulier :

- l'exposition, le contraste, les ombres, les noirs, les hautes lumières et les blancs ;
- l'ouverture des fichiers RAW Canon CR2 et CR3 ;
- les dominantes de couleur observées sur les CR3 ;
- la balance des blancs et la nuance vert ↔ magenta ;
- l'intégration des réglages dans l'interface QML ;
- la compilation et la validation du projet avec et sans LibRaw.

## Problématiques identifiées

### Réglages de lumière

Les réglages `shadows`, `blacks` et `highlights` appliquaient initialement le même multiplicateur global que l'exposition. Ils ne ciblaient donc pas réellement les plages tonales correspondantes.

L'exposition n'était par ailleurs pas toujours appliquée dans le pipeline de rendu. Le contraste était également traité comme un simple facteur global, sans pivot autour du gris moyen.

### Ouverture des fichiers CR3

Le provider contenait une détection incorrecte du format :

- l'URL complète `image://editor/...` était comparée directement à `"cr3"` ;
- cette comparaison ne pouvait jamais détecter correctement l'extension ;
- le décodage CR3 n'était donc pas correctement relié au chemin d'ouverture QML.

Le décodage RAW était également dupliqué entre `ImageEditor` et le provider.

### Dominantes et voile sur les CR3

Les CR3 présentaient successivement :

- une dominante rose/magenta ;
- une dérive vers le vert ;
- un voile blanc ou une image trop éclaircie.

Une première neutralisation automatique calculée sur l'image RGB 8 bits a été ajoutée, mais l'analyse a montré que cette correction était fragile :

- elle intervenait après le développement RAW ;
- elle se basait sur une moyenne globale de pixels supposés neutres ;
- elle pouvait interpréter à tort le contenu de la scène comme une dominante ;
- elle pouvait modifier les niveaux et créer un rendu délavé.

RawTherapee a été consulté, notamment `canon_cr3_decoder.cc` et `dcraw.h`. Cette comparaison a montré que le décodeur CR3 ne doit pas être réduit à une simple conversion RGB : l'extraction de la piste CRX, la balance des blancs, la matrice caméra et le dématriçage sont des étapes distinctes.

### Compilation

Une erreur de compilation est apparue après la séparation des profils CR2 et CR3 :

```text
loadRawImage(...) : candidate expects 3 arguments, 4 provided
```

L'appel dans `imageeditor.cpp` n'avait pas été mis à jour après la modification de la signature.

## Corrections réalisées

### Pipeline de rendu tonal

Dans [imageeditor.cpp](../../../src/editor/imageeditor.cpp) :

- l'exposition est appliquée globalement avec un facteur basé sur les stops :
  `pow(2.0, brightness / 100.0)` ;
- le contraste pivote autour de `0.5`, c'est-à-dire autour du gris moyen ;
- les ombres, les noirs, les hautes lumières et les blancs utilisent des masques de luminance différents ;
- les valeurs intermédiaires sont traitées en flottants entre `0` et `1` avant limitation et conversion en 8 bits ;
- l'aperçu et l'export utilisent le même `renderImage`.

### Gestion des blancs

Un réglage `whites` a été ajouté :

- dans `ImageEditor::Settings` ;
- avec la méthode `setWhites(int)` ;
- dans `Main.qml` ;
- dans `Setting.qml` ;
- dans la réinitialisation des réglages.

Les blancs ciblent les tons les plus proches du blanc, distincts des hautes lumières.

### Gestion CR2/CR3

Le décodage est centralisé dans [RawDecoder.cpp](../../../src/raw/RawDecoder.cpp).

Deux fonctions publiques distinctes sont maintenant utilisées :

```cpp
QImage loadCr2(...);
QImage loadCr3(...);
```

Le choix est effectué en fonction de l'extension dans `ImageEditor` et dans `ImageProvider`.

Le profil CR3 désactive l'éclaircissement automatique de LibRaw :

```cpp
raw.imgdata.params.no_auto_bright = 1;
```

Le profil CR3 utilise aussi la balance des blancs caméra afin d'éviter la dérive verte observée avec la balance automatique.

Le profil CR2 conserve le comportement précédent, déjà jugé satisfaisant.

La neutralisation globale post-développement des couleurs a été retirée, car elle pouvait être la cause du voile ou d'une dérive artificielle.

### Interface couleur

Dans le `ColumnLayout` « Couleur » de [Main.qml](../../../src/qml/Main.qml) et dans [Setting.qml](../../../src/qml/Setting.qml) :

- une case « Balance des blancs automatique » a été ajoutée ;
- un curseur « Nuance vert ↔ magenta » a été ajouté ;
- la valeur négative de la nuance se dirige vers le vert ;
- la valeur positive se dirige vers le magenta ;
- l'ancien contrôle « Température », qui appelait incorrectement `setBrightness`, a été supprimé.

Le changement de balance des blancs redécode les fichiers CR2/CR3. Le réglage de nuance est appliqué dans le pipeline de rendu et concerne donc l'aperçu ainsi que l'export.

### Validation de compilation

Les deux configurations suivantes ont été compilées avec succès dans WSL Ubuntu et Ninja :

1. LibRaw désactivé :

```text
cmake -S . -B build-wsl-nolibraw -G Ninja -DIPR_ENABLE_LIBRAW=OFF
cmake --build build-wsl-nolibraw --parallel 4
```

2. LibRaw activé avec LibRaw 0.21.2 :

```text
cmake -S . -B build-wsl-libraw -G Ninja -DIPR_ENABLE_LIBRAW=ON
cmake --build build-wsl-libraw --parallel 4
```

Les deux builds ont abouti.

## État actuel et limites

- Le code compile avec et sans LibRaw dans WSL.
- La séparation CR2/CR3 est en place.
- Le rendu réel sur des fichiers CR2 et CR3 représentatifs doit encore être vérifié visuellement sur Windows avec plusieurs boîtiers et conditions de lumière.
- Il n'existe pas encore de tests automatisés comparant les niveaux, les couleurs et les histogrammes d'un RAW avant et après traitement.
- Les paramètres de développement RAW restent limités par rapport à RawTherapee : le décodeur LibRaw produit actuellement une image RGB 8 bits sRGB, sans conservation d'un tampon RAW linéaire haute précision, sans profil DCP et sans contrôle avancé du niveau noir/blanc ni du dématriçage.

## Architecture actuellement implémentée

Le chemin de traitement est actuellement organisé ainsi :

```text
QML (Main.qml / Setting.qml)
    -> appels Q_INVOKABLE sur ImageEditor
    -> Settings conservés par ImageEditor
    -> décodage source en QImage
         RAW CR2/CR3 : loadCr2/loadCr3 -> LibRaw -> RGB888 sRGB 8 bits
         formats standard : QImageReader -> QImage
    -> m_original en RGBA8888
    -> renderImage() avec OpenCV
         séparation RGB/alpha
         réglages sur CV_32FC3 normalisé entre 0 et 1
         reconversion en 8 bits RGBA
    -> aperçu via ImageProvider, rendu asynchrone
       ou export via QImageWriter, tâche asynchrone
```

Les réglages d'exposition, contraste, nuance, tons, niveaux de gris et flou sont conservés dans `ImageEditor::Settings`. L'aperçu et l'export appellent le même `renderImage()`, ce qui limite les différences entre ces deux sorties.

Il est important de distinguer `CV_32FC3` de données linéaires : le tampon est actuellement un RGB sRGB 8 bits converti en flottants normalisés. Cette opération améliore la précision des calculs, mais ne linéarise pas la courbe sRGB et ne récupère pas les informations perdues lors du développement RAW en 8 bits.

### Architecture cible pour la gestion avancée des couleurs

La gestion avancée des couleurs n'est pas encore implémentée. L'évolution recommandée est de séparer clairement les responsabilités :

```text
Fichier source
    -> décodage / profil d'entrée
    -> espace de travail flottant linéaire à grande dynamique
    -> balance des blancs et corrections colorimétriques
    -> exposition et traitements tonals
    -> conversion de sortie vers sRGB ou profil cible
    -> aperçu et export issus du même résultat
```

Les règles d'architecture recommandées sont :

1. **Décodage RAW** : demander à LibRaw une sortie 16 bits et, si la configuration le permet, une sortie linéaire avec matrice caméra documentée. Préserver les niveaux et éviter l'auto-éclaircissement. Les choix CR2/CR3 restent isolés dans des profils de décodage distincts.
2. **Entrées non RAW** : lire le profil ICC incorporé lorsqu'il existe ; convertir les pixels vers l'espace de travail plutôt que supposer que chaque entrée est sRGB.
3. **Espace de travail** : conserver les pixels sous forme de flottants linéaires (par exemple `CV_32FC3`) avec une plage dynamique pouvant dépasser `[0,1]`. Ne pas écrêter au blanc après chaque opération.
4. **Balance des blancs** : appliquer gains RGB et compensation vert/magenta avant la conversion de sortie, sans estimer arbitrairement une neutralité depuis toute l'image. Séparer la balance caméra, l'option automatique et la correction manuelle.
5. **Transformations couleur** : centraliser les conversions caméra ↔ espace de travail et utiliser des profils ICC/DCP ou les matrices LibRaw disponibles ; documenter l'ordre des matrices et les hypothèses de primaires.
6. **Traitements** : effectuer exposition et courbes dans l'espace et le domaine définis par leur opération ; les corrections de teinte/saturation doivent éviter de modifier involontairement la luminance.
7. **Sortie** : appliquer une conversion de gamut et l'encodage sRGB (ou le profil choisi) une seule fois, en bout de chaîne, puis quantifier en 8/16 bits selon le format.
8. **Partage du pipeline** : exposer une fonction de rendu commune qui produit une image de sortie avec espace colorimétrique connu. L'aperçu et l'export consomment ce même résultat.

Cette séparation doit être introduite progressivement, car le passage actuel d'une image RAW à `QImage::Format_RGB888` sRGB est une frontière avec perte. Pour tirer parti de données RAW 16 bits, le résultat du décodeur et le stockage de l'image originale devront également évoluer ; remplacer uniquement le type OpenCV par des flottants ne suffira pas.

## Étapes restantes et directions recommandées

### 1. Ajout d'une vraie gestion des couleurs

Suivre l'architecture cible décrite ci-dessus. Priorités concrètes :

- passer le décodeur RAW vers une sortie 16 bits et définir explicitement la courbe de transfert de LibRaw ;
- faire transiter l'image originale et le rendu interne en flottants linéaires, sans écrêtage anticipé ;
- définir les métadonnées ou types qui identifient l'espace de chaque image ;
- utiliser LittleCMS ou un mécanisme ICC équivalent pour les entrées/sorties profilées ;
- différer l'encodage sRGB et la quantification jusqu'à l'aperçu final ou l'export ;
- valider le résultat sur une charte couleur et des images CR2/CR3 comparées à un logiciel de référence.

### 2. Réduction du bruit

Direction recommandée :

- ajouter un réglage de luminance et un réglage de chrominance séparés ;
- appliquer la réduction du bruit avant l'accentuation et avant les courbes ;
- commencer par un filtre bilatéral ou un filtre guidé pour une implémentation simple ;
- prévoir ensuite une méthode plus adaptée aux RAW, comme une réduction dans l'espace YCbCr ou Lab ;
- ne pas appliquer la réduction du bruit aux images déjà très petites sans seuil de résolution ;
- ajouter un aperçu à 100 % pour évaluer la perte de détail.

Pour un premier ajout sûr, la réduction du bruit doit être optionnelle et limitée aux images RAW, avec des valeurs par défaut nulles.

### 3. Courbes de tonalités

Direction recommandée :

- ajouter une courbe paramétrée par des points de contrôle `(entrée, sortie)` ;
- interpoler les points avec une spline monotone ou une interpolation linéaire contrôlée ;
- appliquer la courbe séparément sur la luminance, et non indépendamment sur les trois canaux RGB, afin d'éviter les dérives de teinte ;
- conserver une courbe identité par défaut ;
- ajouter des préréglages simples : contraste faible, contraste moyen, contraste fort et courbe en S ;
- travailler en flottant avant la conversion finale en sRGB.

La courbe doit être appliquée après l'exposition et la balance des blancs, mais avant les opérations de sortie telles que l'encodage JPEG.

### 4. Correctif sur l'export des images

Directions à vérifier :

- vérifier que l'export utilise exactement le même pipeline que l'aperçu ;
- contrôler l'espace colorimétrique du fichier exporté ;
- convertir explicitement en `QImage::Format_RGB888` ou `Format_RGBA8888` selon le format cible ;
- supprimer le canal alpha pour JPEG ;
- conserver l'alpha pour PNG lorsque cela est souhaité ;
- vérifier l'orientation et les métadonnées EXIF ;
- appliquer la qualité uniquement aux formats qui la supportent ;
- vérifier les profils ICC incorporés ;
- comparer les histogrammes de l'aperçu et de l'image exportée après relecture.

Un test de non-régression devrait exporter une image avec des réglages non neutres, la relire, puis comparer :

- dimensions ;
- présence ou absence d'alpha ;
- moyenne et écart-type par canal ;
- histogramme ;
- orientation ;
- profil colorimétrique.

### 5. Tests RAW dédiés

Avant de poursuivre les réglages avancés, il est recommandé de constituer un petit jeu de fichiers :

- un CR2 et un CR3 provenant de boîtiers différents ;
- une scène avec une charte grise ou blanche ;
- une scène avec des tons chair ;
- une scène contenant des zones très sombres et très claires ;
- plusieurs températures de lumière.

Pour chaque fichier, il faudra comparer :

- rendu CR2/CR3 dans IPR ;
- rendu dans RawTherapee ;
- balance des blancs ;
- niveau des noirs ;
- niveau des blancs ;
- histogramme ;
- dominante verte ou magenta ;
- voile ou perte de contraste.

## Ordre de priorité conseillé

1. Valider visuellement les profils CR2/CR3 sur un jeu de fichiers représentatif.
2. Stabiliser le pipeline linéaire et la gestion des espaces colorimétriques.
3. Corriger et tester l'export.
4. Ajouter les courbes de tonalités.
5. Ajouter la réduction du bruit.
6. Ajouter les profils ICC/DCP et les contrôles colorimétriques avancés.
